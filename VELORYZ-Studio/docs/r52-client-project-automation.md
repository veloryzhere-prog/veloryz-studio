# R52 — Client and Project Operations / automated onboarding architecture

## Current integration and R52.1

The new owner-only Project Operations workspace at /admin/#/project-operations reads the existing client directory (up to 200 workspaces), paginated enquiry inbox (25 per page) and email configuration endpoint. It provides project portfolio, status pipeline, intake and automation blueprint views, links directly into the existing private project editor, and distinguishes a reference match from a database-wide relationship proof. Client Rooms retains the current project/milestone/file/approval/message/invitation editors and owner-only controls. The mail history is scoped to the selected project and distinguishes loading, failed and empty responses. The public portfolio CMS remains separate. All changes in R52.1 are owner UI changes; no automatic email, code issuance, billing, migrations or provider deployments were performed.

The deployed veloryz-client-portal-api (observed version 13) already provides accept, send-summary, invite, delivery and mail-events endpoints, a project-summary PDF renderer and Gmail SMTP transport. The existing workflow explicitly requires owner action and uses the original request reference. Do not reuse the owner-only acceptance endpoint from a public browser or make it anonymous. The current enquiry endpoint accepts multiple request types, including payment and bug reports. It cannot safely use a client-supplied message prefix to determine that a project has been ordered.

## R52.2 — Verified project submission contract

Add a dedicated server-side Creator submission contract (or authenticated internal submission event), explicit project intent, versioned structured brief, validated consent, rate limiting/anti-bot challenge, server-computed pricing and catalog revision, normalized recipient, request UUID/idempotency key and a server-side fingerprint. Keep general enquiries, support, bookings and bugs out of onboarding. Persist the exact original brief and quote snapshot; do not trust client totals or free-text estimates as an agreed price. Existing request retries must return the same identifiers, without sending another welcome email. Initial status: submitted / pending review; do not mark accepted or reserve a delivery date before owner approval. For existing clients, do not merge accounts by unverified email; link only after verification. Return request reference and status without returning a secret code or any other client's existence.

## R52.3 — Private transactional data model

Design migrations after inspecting current tables and constraints. Reuse existing studio_enquiries, studio_client_projects, studio_client_invites, studio_client_email_events and finance records when compatible. Add a private stable client identity with unique generated public-facing client ID (e.g. VZ-C- plus random identifier), project display ID (VZ-P-...), request-to-project unique constraint, and an immutable onboarding snapshot. All new tables remain in the isolated studio schema, RLS enabled, no public grants. Maintain FK relationships between verified identity, request, project, quote, document, invite and job. Separate lifecycle states: request submitted, pending review, accepted, delivery in progress, closed; access states: pending verification, invited, activated, expired, revoked; document states: estimate/provisional, approved invoice, void; mail states: queued, processing, SMTP accepted, failed, uncertain, exhausted. Admin shows real IDs and timestamps; no plaintext invitation codes in DB views, exports or logs. Existing manual acceptance must be idempotent with the auto-created workspace, and preserve the original brief.

Atomic transaction: validate request -> create pending workspace -> write pricing snapshot -> create onboarding outbox job with unique event key -> commit. No network SMTP call inside a database transaction. If any DB write fails, roll back the entire operation. Return success only after durable commit. Keep automation disabled by default until owner enables it after tests; ensure a kill switch can stop sends without discarding jobs.

## R52.4 — PDF document and access pack

Initial PDF is a pro forma invoice/estimate, explicitly provisional, not a demand for payment or a tax invoice. Include studio identity, contact, client ID, project ID, request reference, submitted scope, server-calculated INR line items in integer paise, optional discounts only when actually authorized, estimate total/range, assumptions, validity, and pending-review status. If no reliable price exists, use an estimate/brief without invented amount. Final invoice generation requires approved commercial amount and configured legal/tax details, and unique sequential document numbering appropriate to the applicable jurisdiction; no invented GST registration or payment status. Version issued files; do not silently overwrite or duplicate a final invoice. Store PDFs in private storage linked to the project; authorization checks for downloads. Existing project summary is not a final invoice.

Generate a cryptographically random, single-use, time-limited access credential server-side; hash for validation, bind to the precise project and recipient, enforce attempt limits, consume atomically, revoke on email change, and issue a scoped portal session on successful verification. A pending-review portal may display only the submission and provisional document; do not reveal other projects or internal notes. Use the existing portal login mechanism where possible after verifying it supports the new state. The mail includes a stable client ID, project reference, activation code and canonical https://veloryz.online/client/ link. Prefer short expiry for emailed activation. Never put access secrets in PDF attachments or logs; redact from admin. If retry needs the original token, keep it encrypted under a server-only key with strict TTL and erase after final outcome, or issue a replacement only through an explicit controlled action that invalidates the old token. Do not rotate codes blindly on automatic retries.

## R52.5 — Durable email delivery

Use a private transactional outbox and a bounded scheduled worker (Supabase Queues/PGMQ or compatible durable DB job claims, subject to verified deployment configuration). Claim jobs with lease and unique idempotency key; validate job status and project recipient before sending. Reuse existing Gmail transport and PDF generator; use stable Message-ID and one welcome message per event. Trigger immediately after commit and use a durable periodic sweep as recovery. Target first attempt within seconds under normal conditions, not guaranteed inbox delivery. Record SMTP acceptance separately from confirmed delivery. Retry transient failures with backoff and jitter (e.g. 1m, 5m, 30m, 2h, bounded attempts); pause on missing credentials, permanent recipient failure or exhausted retry. Ambiguous SMTP acceptance/timeouts need an uncertain state and operator review: SMTP is not exactly-once, stable Message-ID does not guarantee deduplication. Do not silently resend to a different address. Never log the code, PDF contents, mail credentials or full private SMTP responses. Send only to the user-provided validated recipient, with abuse prevention, per-recipient/per-IP limits, and no marketing enrollment. Consider sending a verification-only email before including a private PDF if mailbox ownership is not established; treat initial email delivery to a mistyped address as a privacy risk. Ensure admin cannot manually send the same welcome event concurrently with the worker.
