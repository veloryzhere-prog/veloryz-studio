Dark mode and authenticated screenshot certification are not included in R51.1. The reference images are design inspiration, not pixel-perfect clones.

## R51.11 — Infrastructure & System Control / Flightdeck

### Design research and architecture

Flightdeck is intentionally distinct from the light content-management surfaces: a graphite instrument canvas with mint observation accents, monospaced measurement labels, a numbered logical topology, a selected-node inspector, and a separate release journal. The five views serve different operator tasks instead of presenting an undifferentiated collection of status cards. Desktop topology compresses to two columns and then one; data tables scroll inside their own container. State labels use text and icon shapes as well as color, keyboard focus is visible, and reduced-motion preferences disable the scoped transitions.

Research references:
- Google SRE monitoring: https://sre.google/sre-book/monitoring-distributed-systems/ — distinguish latency, traffic, errors and saturation; do not call occasional probes uptime.
- Grafana dashboard guidance: https://grafana.com/docs/grafana-cloud/learn-and-build/visualizations/dashboards/build-dashboards/best-practices/ — symptom-led observations and explicit service boundaries.
- Cloudflare deployment/rollback guidance: https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/ — code versions are separate from persistent resources and CMS publications.
- Supabase observability and advisors: https://supabase.com/docs/guides/observability — inspect database, auth, storage and provider-native diagnostics rather than deriving a global security or health score from configuration flags.

### Functional coverage

Flightdeck contains 14 explicitly requested same-origin GET checks: public HTML/deployment identity, core backend, published CMS, owner state, runtime configuration, media inventory, official logo image, original motion video, shared AI configuration, client email configuration, content preflight, anonymous owner-access denial, CMS history, and documentation source. Full runs are limited to three simultaneous requests, each with a timeout. The response contract determines the result; configuration is not marked as a verified live inference or delivery. Only bounded summaries are retained, with no client content, secrets, raw response bodies or uploaded files in the exported report. Anonymous denial is checked without credentials; no redirect is followed. Public assets use a bounded Range request and response cancellation. Owner API checks use existing authorization. The ten most recent full-run timing samples and manual readiness attestations are tab-memory only. No background polling, continuous monitoring or fake traffic is added.

The release view uses the reported deployed HTML headers, distinguishes public and owner CMS revision observations, and lists up to 50 actual CMS history records. A guarded restore invokes the existing version-checked restore-to-draft API only; unsaved changes block restore and publication requires a separate action. Worker rollback remains an explicit provider-side procedure with resource compatibility checks. Build metadata now stamps R51.11 and the checked-out Git revision; fallback metadata retains an unknown commit rather than inventing one.
